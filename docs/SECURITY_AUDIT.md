## 3. Модель безопасности v0.2

1. **Обнаружение только читает.** `WindowsHidEnumerator`: `CreateFile` с `desiredAccess = 0`, чтение дескриптора/строк. Запрещённые API (`WriteFile`, `HidD_SetFeature`, `HidD_GetFeature`, `ReadFile`, `DeviceIoControl`, …) не вызываются. Устройства других производителей **не открываются вообще**.
2. **Единая точка записи.** Записать байты можно только через `IHidTransport.SendAsync(ApprovedWrite)`. Тип `ApprovedWrite` имеет `internal`-конструктор, его выпускает только `WriteGate`. UI и сервисы не могут обойти проверки.
3. **`WriteGate` (отказ по умолчанию).** Для реального устройства одновременно нужны: (а) разрешение владельца на текущий сеанс (ввод фразы; не сохраняется), (б) запись в `verified-protocols.json` — «команда × точный дескриптор интерфейса», внесённая владельцем **после** испытания, (в) команда не из классов `Destructive/Unknown`, (г) VID 0C45, не загрузчик (7140), интерфейс vendor-defined, (д) побайтное совпадение длины отчёта с дескриптором. Для симулятора (`sim://`) реального железа нет — арминг не нужен, но `Destructive/Unknown` блокируются и здесь.
4. **Реестр пуст.** В поставке подтверждённых записей: **0**. Следовательно, записать что-либо в реальную клавиатуру из этой сборки **невозможно**. Это проверяется тестами и видно на странице «Безопасность».
5. **Блокируются навсегда**: сброс (0x0F), SET_KEY/FN_KEY/MACRO, SET_GAME_MODE (частота опроса/debounce — значения не документированы). Загрузка этих записей в реестр отклоняется.
6. **Всё или ничего.** Перед отправкой последовательности проверяются **все** пакеты; если хотя бы один заблокирован — не уходит ни один.
7. **Интерфейс выбирается без догадок**: нужен единственный vendor-интерфейс с точным совпадением длины; при неоднозначности — отказ.
8. **Журнал локальный**, пути HID, длинные hex-токены (серийные/instance-id) и имя пользователя маскируются; телеметрии нет; сети нет.

## 4. Автоматические «рельсы» (SourceAuditTests, 6 тестов)

Падают при попытке (в том числе ИИ-ассистентом) добавить: запись в устройство вне `WindowsHidTransport.cs`; открытие устройства с ненулевым доступом в перечислителе; `HttpClient/Socket/Process.Start/Registry/Assembly.Load`; build-хуки в csproj; пакеты в проектах приложения; `Invoke-WebRequest`/`Set-ExecutionPolicy`/`-ExecutionPolicy Bypass`/`pnputil`/`devcon` в скриптах. Работоспособность проверена «мутационно»: внесение `WriteFile` и `HttpClient` в Core роняет тесты.

## 5. Остаточные риски (честно)

- `WindowsHidTransport` содержит рабочий код записи (нужен для этапа аппаратных проверок). Он инертен, пока реестр пуст, но после того как владелец добавит записи, ответственность за корректность этих записей лежит на нём — см. `HARDWARE_ACCEPTANCE.md`.
- Чтение строк продукта/производителя (`HidD_GetProductString`) — запрос к HID-классу (стандартный дескриптор USB), не конфигурационная команда; серийный номер не читается.
- Описания протокола получены из чужих репозиториев; «подтверждено» в UI означает только чтение дескрипторов на этом ПК, не работу команд.

## 6. Изменения модели безопасности в v0.3 (реальная запись под контролем владельца)

Цель итерации — рабочая запись на USB-режиме по подтверждённому эталону, **без ослабления** защиты:

| Было (v0.2) | Стало (v0.3) |
|-------------|--------------|
| Реестр разрешённых команд пуст; запись физически невозможна | Реестр заполняет **только владелец** кнопками «Этапы активации» (RGB → PNG → GIF, строго по порядку); по умолчанию он по-прежнему пуст |
| Запись = (реестр) + (фраза сеанса) | То же + **метка этапа** у каждого пакета: записи реестра привязаны к этапу, пакеты RGB не могут передать картинку, пакеты «PNG» (1 кадр) не пройдут как «GIF» |
| Выбор интерфейса по длине отчёта | По usage page роли (`FF13`/`FF68`) **и** точной длине; неоднозначность — отказ |
| Пакеты без метаданных | Пакеты несут паузы, чтение ответа (handshake), ожидание ACK; ответы устройства пишутся в журнал |
| Запись реестра могла содержать любой Feature04-/AA-идентификатор | Активация создаёт только фиксированные записи этапа: VID 0C45, PID 8009, `FF13`/feature/65 (команды 0x18, 0x13, 0x72, 0x02, 0xF0) и `FF68`/output/4097 (0x72); тесты запрещают `Destructive/Unknown` в записях этапов |
| Транспорт — один класс | Логика транспорта вынесена в `HidTransportCore` (без Win32; тестируется на фейковом устройстве); Win32-вызовы по-прежнему только в `WindowsHidTransport.cs` (аудит-тест) |

Что **не** изменилось: ни одной записи не выполняется без активированного этапа И разрешения сеанса (фраза); дискавери — только чтение (нулевой доступ); чужие VID не открываются; сброс/ремап/макросы/`SET_GAME_MODE` заблокированы навсегда; активация этапа ничего не отправляет; всё-или-ничего на предпроверке; отказ записи при несовпадении длины отчёта.

Новые остаточные риски: (1) команды в этапах подтверждены эталоном, а не KORTY — первая запись KORTY выполняется владельцем по `ACTIVATION_GUIDE.md`; (2) overlapped-ввод-вывод Windows проверен на именованном канале, но не на настоящем HID (HidD_* вызовы без устройства не тестируемы); (3) байт 8 SAVE и FINISH — эмпирические переключатели эталона.

Найденное и исправленное при реализации: буфер overlapped-операции должен быть закреплён (pinned) до завершения I/O — исправлено явным `GCHandle`; округление задержек кадров приведено к JS-семантике (.5 вверх) — найдено golden-тестом.

## 7. Актуальная модель (v1.1)

Пользователь включает управление **одним подтверждением** (без ввода фразы); согласие записывается как набор разрешённых пар «команда × интерфейс» (`verified-protocols.json` в `%LOCALAPPDATA%\KORTY\KeyboardStudio`) и запоминается; отключается на странице «Безопасность». Остальное без изменений: запись только на VID 0C45 / PID 8009 с точным совпадением дескрипторов (FF13 feature 65 Б, FF68 output 4097 Б), метка этапа у каждого пакета, проверка всех пакетов до первой отправки, навсегда заблокированы сброс, ремап, макросы, `SET_GAME_MODE`, неизвестные команды; discovery только читает и не открывает чужие устройства. Разделы 3–6 выше описывают прежнюю схему с вводом фразы — механика реестра и проверок осталась прежней, изменился только способ выдачи согласия.

Блокировка клавиш на ПК (хук клавиатуры) удалена в v1.2: отключение Win / Alt+F4 / Alt+Tab выполняет сама клавиатура через стадию «Настройки» (блок настроек: START, SETTINGS_CFG, данные, SAVE), приложение клавиатуру не перехватывает.
