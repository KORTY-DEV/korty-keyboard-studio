# Исследование протокола AJAZZ AK820 Pro

Дата: 2026-10-08. Для каждого утверждения указано основание: **[SRC]** — исходный код, **[DOC]** — документация проекта, **[REAL]** — реальное чтение дескрипторов на этом ПК (без отправки команд), **[HYP]** — гипотеза.

> Метод. Тексты страниц/файлов получены инструментом веб-чтения, который возвращает пересказ (не побайтную копию). Поэтому числа ниже — второй уровень достоверности; перед этапом аппаратных проверок ключевые значения следует сверить прямым чтением исходников. Кодом чужих проектов программа **не пользуется**: протокольный слой написан заново по описаниям полей (факты о формате не являются охраняемым выражением), ссылки на источники сохранены в `CommandCatalog`.

## 2. Аппаратные факты (общие)

- MCU HFD80CP100 (клон Sonix SN32F299), беспроводной модуль WCH CH582F, внешний flash PY25Q128HA 16 МБ, экран 0.85″ 128×128 GC9107, RTC D8563F **[DOC: wsclx, fpb]**.
- VID 0C45 (Microdia/Sonix). PID: 8009 и/или 800A (кабель), 7140 — ISP-загрузчик (контакты под пробелом; не трогать), FEFE — Bluetooth **[DOC]**. Прошивочный файл штатной прошивки называется `…PID_8009_V1.13_SN32F290.bin` **[DOC: fpb]**.

## 3. Два несовместимых семейства протокола

Классификация по «аппаратной ревизии / прошивке» невозможна: источники не называют ревизий, расходятся даже по одному PID. Поэтому в коде это `ProtocolFamily` и выбирается явно.

| Признак | **AaFrame** (wsclx) | **Feature04** (kabelklaus) |
|---------|---------------------|-----------------------------|
| PID | 8009 (кабель **и** 2.4 GHz), FEFE BT [DOC] | 8009 или 800A; **подтверждён на железе только 800A**; кроме кабеля ничего не доступно [DOC] |
| Тип отчётов | Output, report-id 0, 64 Б (+1 id — «надо перепроверить») | **Feature** 64 Б для команд; **Output 4096 Б** для данных картинки |
| Интерфейс управления | interface 2, usage page **FF68** (в другом месте — FF67 на interface 3 «для macOS») — внутренне противоречиво [DOC] | usage page **FF13** (управление), **FF68** (данные) [SRC app.js] |
| Кадр | `AA cmd len addr(2,LE) opt0 opt1/last opt2 payload…` | `04 cmd sub 00… [8]=en` |
| Подсветка | cmd 0x23, 16-байтный payload, трейлер **AA 55** | START 0x18 → MODE_CFG 0x13 → MODE_DATA → SAVE 0x02 → FINISH 0xF0, трейлер **55 AA** |
| Ответ | magic 0x55, тот же формат | эхо команды, байт 3 = 1 |
| TFT формат кадра | RGB565 LE, 128×128, 32 768 Б | то же |
| TFT заголовок | 256 Б: [0]=N кадров, затем задержки, в **5 мс** единицах (макс 1275 мс), «терминатор 0x00»; остальное 0xFF | 256 Б: [0]=N, [1..N] задержки в **2 мс** (2–510 мс), для одного кадра [1]=0, остальное 0xFF |
| TFT выравнивание | payload кратен 4096? (не указано), чанки 4096+8 | payload дополняется 0xFF до кратного **4096** |
| TFT чанк | 8-байтный заголовок `AA 50 idx(2) total(2) 0x0650` + 4096 Б = 4104 Б; подтверждение приходит как cmd 0x41 | сырой 4096-байтный output-отчёт; ждёт любой input-отчёт ≤300 мс, потерянный ACK не прерывает |
| Завершение | не описано; «экран остаётся на встроенной анимации, нужна последовательность активации» | AKS075: SAVE `04 02 00 00`; gohv: FINISH `04 F0 00 01` |
| Ёмкость | GET_DEVICE_INFO: 255 кадров; оценка «около 30+» | по умолчанию 120, максимум 255 |
| Постоянное хранение | **не описано** | **не описано**; предупреждает «настройки могут пропадать при перезагрузке (переключении режима) — проверьте отключением кабеля» |
| 2.4 GHz | PID тот же 8009; различий протокола не описано | **vendor-интерфейсы по 2.4 GHz недоступны** |
| Состояние проекта | TFT «в разработке», активация не найдена | работает у автора на PID 800A |

Конфликты, которые нельзя разрешить без железа: единица задержки (5 vs 2 мс), порядок трейлера (AA 55 vs 55 AA), роль FF68 (управление vs данные), нужен ли SAVE (0x02 — автор kabelklaus сам блокирует его в сканере как опасную), длина отчёта (64 vs 65), терминатор заголовка.

## 4. Реальный факт с этого ПК ([REAL], 2026-10-08, только чтение)

Сейчас подключён только приёмник **0C45:FDFD «2.4G Dongle»** (кабель отключён). 9 HID-интерфейсов:

| MI/COL | Usage | in/out/feature | Роль |
|--------|-------|----------------|------|
| 00 | 0001/0006 | 9/2/0 | клавиатура (система) |
| 01 | 0001/0002 | 6/0/0 | мышь (система) |
| 02/01…04 | 000C/0001, 0001/0080, 0001/0006, 0001/000E | 3, 2, 16, 9 / 0 / 0 | потребительские, системные, NKRO, … |
| 02/05 | **FFFF/0001** | 4/0/0 | vendor, только вход |
| 03 | **FF60/0061** | 33/33/0 | vendor, in/out 32 Б |
| 04 | **FF60/0061** | 65/65/0 | vendor, in/out 64 Б |

Файлы: `docs/observations/report-2026-10-08-dongle-only.json`, `snapshot-2026-10-08-dongle-only.json`.

Следствия:
1. У донгла **нет** интерфейсов FF13/FF67/FF68 из описаний обоих проектов. Для канала настройки экрана по 2.4 GHz **ни одна из известных схем не применима** без дополнительных данных. Это согласуется с утверждением kabelklaus (по 2.4 GHz vendor-канала нет) и с вашим наблюдением о поведении родной программы.
2. `FF60/0061` — стандартная пара «raw HID» в QMK/VIA [общеизвестное соглашение]; в изученных источниках для штатной прошивки она не описана. Что за протокол на этих интерфейсах — **неизвестно** ([HYP]: проксирование радиомодулем WCH CH582F; не VIA-совместимость штатной прошивки). Ничего туда не отправлялось и не будет без отдельного решения.
3. Предположение «USB = 8009, 2.4 GHz = FDFD» подтверждено **частично**: FDFD действительно присутствует отдельно от кабеля. Привязка 8009 к кабелю требует снимка A (кабель без донгла) — инструмент для этого в «Диагностике → Сравнение».

## 5. Команды (см. `CommandCatalog`)

Полный список с классом риска и источником — страница «Безопасность» приложения. Кратко:
- **Реализованы построители (dry-run и симулятор)**: AaFrame 0x23 SET_LED_EFFECT, 0x10 GET_DEVICE_INFO, 0x50 TFT-чанки; Feature04 START/MODE_CFG/MODE_DATA/IMAGE_CFG/SAVE/FINISH.
- **Блок настроек (0x17 SETTINGS_CFG, класс PersistentSetting, источник — статический анализ фирменной программы)**: START `04 18`, `04 17 01` (байт 8 = 1), 64-байтовые данные `[1]=01 [2]=Alt+Tab [3]=Alt+F4 [4]=Win [5]=fn_switch(1) [6]=сон 0..3 [8]=отклик клавиш 1..5 [62..63]=AA 55`, SAVE `04 02`. Байт 8 у kabelklaus назван «standby» — по фирменной программе это уровень отклика. На железе не проверено.
- **Не реализованы, класс Unknown**: часы (0x28 / TIME_CFG), per-key RGB (0x24), встроенные анимации (0x51 — «догадка» в источнике).
- **Заблокированы навсегда (Destructive)**: 0x0F factory reset, 0x22/0x26 ремап, 0x25 макросы, 0x21 SET_GAME_MODE (содержит частоту опроса, debounce, sleep — допустимые значения нигде не документированы).

## 7. Обновление 2026-10-09: рабочий эталон на вашей клавиатуре

Владелец лично проверил веб-конфигуратор kabelklaus в USB-режиме: подключение, изменение RGB и загрузка PNG на TFT работают, клавиатура продолжает работать. Поэтому для USB-режима рабочим эталоном считается **семейство Feature04**; повторного исследования AA-семейства не требуется (оно оставлено в коде как неподтверждённое).

**Точный исходник прочитан целиком** (`app.js` 1659 строк, `index.html`; SHA-256 `app.js` = `52e8215c…0844`) — [SRC], уже не пересказ. Подтверждено/уточнено:

| Факт | Основание |
|------|-----------|
| Отчёты команд — feature, report id `0x00`, 64 байта данных (`sendFeatureReport(0x00, data64)`, «вариант A» — единственный, подтверждённый на железе) | `app.js: frame(), sendFeature()`; `index.html: «Variant A matches this keyboard descriptor and is confirmed on real hardware»` |
| Чанки картинки — `sendReport(0x00, chunk4096)` на интерфейсе FF68; после каждого ждётся input-отчёт до 300 мс; нет ACK — только предупреждение | `app.js: #imgUpload` |
| Каждая feature-команда: отправка → пауза → `receiveFeatureReport(0)` («handshake»); ошибка чтения не критична | `app.js: handshake(), sendFeature()` |
| Подсветка: START(`04 18 00`, b8=1) → 40 мс → handshake → MODE_CFG(`04 13 00`, b8=1) → 40 мс → handshake → MODE_DATA → 40 мс → SAVE(`04 02 00`, b8=0 по умолчанию) → 100 мс → handshake → [FINISH только если включён] | `app.js: #rgbApply, finalize()` |
| MODE_DATA: `[0]=режим, [1..3]=RGB, [8]=радуга(0/1), [9]=яркость≤5, [10]=скорость≤5, [11]=направление, [14..15]=55 AA` (вторичного цвета нет) | `app.js: modeDataPacket()` |
| 20 режимов с названиями: Off, Static, Key on, Key off, Glitter, Falling, Colourful, Breathe, Spectrum, Outward, Scroll, Roll, Rotate, Explode, Launch, Ripple, Flow, Pulse, Tilt, Shuttle; направление — только Scroll/Roll/Flow/Tilt | `app.js: LIGHT_MODES`; текст страницы |
| Картинка (вариант по умолчанию AKS075): START(`04 18 00`, b8=**0**) → handshake → IMAGE_CFG(`04 72 03`, b8/b9 = число чанков LE) → handshake → чанки → SAVE(`04 02 00`, b8=0) → handshake. Вариант gohv: START b8=1, CFG sub 2, закрывается FINISH(`04 F0 00`, b8=1) | `app.js: #imgUpload`, `index.html: imgVariant` |
| Заголовок 256 Б: `[0]=N`, `[1..N]=round(мс/2)` в диапазоне 1..255 (**округление .5 вверх, как JS `Math.round`**), для одного кадра `[1]=0`, остальное `0xFF`; кадры RGB565 LE; всё дополняется `0xFF` до кратного 4096; по умолчанию максимум 120 кадров (до 255) | `app.js: encodeDelay(), #imgUpload, rebuildFrames()` |
| Интерфейсы: управление — usage page `FF13`, данные — `FF68`; допустимые PID `8009`, `800A` (800A отмечен «на реальном железе подтверждён») | `app.js: UP_CONTROL, UP_DATA, PIDS_WIRED` |

**Реальные дескрипторы кабеля** ([REAL], только чтение, 2026-10-09; `docs\observations
eport-2026-10-09-cable-and-dongle.json`): `0C45:8009`, MI03 `FF13/0001` in/out/feature = 65/65/65; MI02 `FF68/0061` in/out/feature = 65/4097/0; MI01/COL05 `FFFF/0001` (вход 4 Б); системные интерфейсы клавиатура/мышь/consumer. Это в точности «подтверждённые HID-дескрипторы» из задания и подходит под Windows-буферы 65 Б (feature) / 4097 Б (output) / 65 Б (input-ACK).

**Исправленные расхождения** (ранее «не разрешимые без железа»): единица задержки для USB-режима — **2 мс** (не 5); трейлер подсветки в MODE_DATA — **55 AA**; FF13 — управление (feature), FF68 — данные (output 4096); SAVE (`0x02`) — штатный завершающий шаг каждой передачи в эталоне (не «опасная» команда: его собственный сканер лишь не отправляет `0x02` вслепую).

**Остаётся неподтверждённым:** байт 8 команды SAVE и необходимость FINISH для сохранения после перезагрузки (эталон делает их переключаемыми — в KORTY это «Параметры протокола»); ёмкость экрана; поведение при смене USB↔2.4 GHz; донгл по-прежнему не имеет интерфейсов FF13/FF68, поэтому настройка экрана по 2.4 GHz этим протоколом невозможна.
